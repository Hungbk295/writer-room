01 · Outcome

Kết quả cần đạt

Daemon, Spy, Team workflow, HTTP, MCP, CLI và Training tiếp tục giữ nguyên contract nghiệp vụ, nhưng dữ liệu quan hệ được đọc/ghi từ Supabase Postgres qua repository bất đồng bộ; schema được tái lập hoàn toàn từ migration SQL có version trong Git.

Mô hình cutover
Offline

Đề xuất phê duyệt: đợt này migrate Team + Spy sang Supabase; giữ pipeline JSONL, Formula JSON, Writer Packs, manifests và binary artifacts trên filesystem. Consolidation các nguồn này là project sau.
Hard gate số 1 — mô hình phân phối: nếu Writer Room được cài trên máy của người dùng khác, tuyệt đối không nhúng Postgres URL, database password hoặc Supabase secret key vào Tauri/daemon. Khi đó phải đặt một backend tin cậy ở giữa, hoặc dùng Data API với Supabase Auth + RLS. Kết nối Postgres trực tiếp chỉ phù hợp với daemon chạy trên hạ tầng/máy do chính chủ hệ thống kiểm soát.

04 · Decision gates

Quyết định bắt buộc trước khi code

Không bắt đầu implementation khi một quyết định dưới đây còn mơ hồ.

ADR-S1
Phạm vi
Team-only, Team + Spy, hay cả filesystem state?
ĐỀ XUẤT Team + Spy; filesystem phase sau.
ADR-S2
Trust boundary
Daemon chạy trên máy tin cậy hay được phân phối cho end-user?
BẮT BUỘC Chọn direct Postgres hoặc trusted API/Auth + RLS.
ADR-S3
Connection mode
Direct IPv6, Supavisor session hay transaction mode?
Persistent daemon: direct nếu có IPv6; nếu IPv4-only dùng session pooler. Migration/backup luôn dùng direct.
ADR-S4
Offline contract
Ứng dụng có bắt buộc chạy khi mất mạng?
Supabase remote làm mất offline-first; nếu bắt buộc cần local cache/outbox, là scope riêng.
ADR-S5
Data access
Postgres repository hay supabase-js/Data API?
ĐỀ XUẤT Server-side Postgres repository; không đổi domain API sang Data API.
ADR-S6
Security surface
Private schema hay public API + RLS?
ĐỀ XUẤT Schema writer_room không expose Data API; least-privilege DB role.
ADR-S7
Transcript search
Native FTS, PGroonga hay giữ SQLite search?
Benchmark corpus tiếng Việt; PGroonga là candidate, không tự động là đáp án.
ADR-S8
Environment & plan
Dev/staging/prod, region, Free/Pro, backup/PITR?
Production không dùng Free nếu không chấp nhận auto-pause và thiếu managed daily backup.
ADR-S9
Cutover & concurrency
Maintenance hay dual-write; một hay nhiều daemon?
ĐỀ XUẤT Maintenance cutover, single-daemon giai đoạn đầu.
05 · Delivery roadmap

Roadmap triển khai P0–P7

Mỗi phase có deliverable độc lập và exit gate. Không gộp sync→async, dialect rewrite và data cutover vào một patch.

P0

Architecture & baseline freeze

Chốt phạm vi, contract và điểm xuất phát có thể tái lập.

HARD GATE
Exit gate: không còn quyết định implementation-impacting chưa xác nhận; baseline tái lập được.
P1

Async repository seam trên SQLite

Đổi boundary đồng bộ sang bất đồng bộ nhưng chưa đổi database.

RỦI RO CAO
Exit gate: chạy SQLite adapter nhưng API behavior không đổi; toàn bộ baseline tests xanh.
P2

Supabase foundation & environments

Có local, staging và production workflow tái lập được bằng Supabase CLI.

FOUNDATION
Exit gate: clone mới chạy supabase db reset tạo đúng schema/seed; staging được deploy từ Git, không drift qua Dashboard.
P3

Postgres schema & repositories

Port query sang PostgreSQL mà giữ nguyên semantic và concurrency contract.

IMPLEMENT
Exit gate: cùng repository contract suite pass trên SQLite và Postgres; search đạt ngưỡng đã phê duyệt.
P4

Security & operational contract

Không biến migration database thành lỗ hổng credential hoặc Data API.

SECURITY GATE
Exit gate: credential extraction review pass; anon/authenticated không đọc được bảng nội bộ; DB-down có lỗi rõ và phục hồi được.
P5

Importer, verifier & rehearsal

Chứng minh data movement lặp lại được trước change window.

NO-GO GATE
Exit gate: verifier 100%; rerun không duplicate; search index rebuild và rollback rehearsal pass.
P6

Production cutover

Chuyển source database có kiểm soát trong maintenance window.

CHANGE WINDOW
Exit gate: smoke pass, không mismatch, không hidden fallback SQLite và không credential/policy failure.
P7

Observation, restore & cleanup

Chứng minh vận hành Supabase bền vững trước khi tháo kiến trúc cũ.

POST-CUTOVER
Exit gate: restore drill pass; rollback window đóng; không còn runtime dependency SQLite.

07 · Data movement

Data migration & verification

Thứ tự import Spy

  1. operations
  2. spy_runs
  3. channels
  4. video_snapshots
  5. video_transcripts
  6. transcript_segments
  7. frame_samples
  8. metrics và profiles

schema_version cũ chỉ là dữ liệu audit; Supabase CLI dùng supabase_migrations.schema_migrations. FTS shadow tables không import.

Verifier bắt buộc

  • Row count và tập primary key giống nhau.
  • 0 FK orphan; báo riêng soft reference orphan.
  • JSON semantic-equal 100%.
  • Timestamp đúng UTC và millisecond.
  • Numeric min/max/sum hoặc chunk checksum.
  • Identity sequence last_value lớn hơn ID tối đa.
  • Artifact path, size và SHA-256 hợp lệ.

Target type policy

UUID hợp lệ           → uuid
SHA-256               → text + CHECK(length = 64 và lowercase hex)
business identifier   → text/varchar + explicit UNIQUE/check contract
Vietnamese content    → text (PostgreSQL UTF-8)
timestamps            → timestamptz, UTC, mapper emits ISO-8601 Z
YouTube counters      → bigint; JS string/BigInt contract
duration / media time → double precision
structured payload    → jsonb
large prose           → text
SQLite autoincrement  → bigint GENERATED BY DEFAULT AS IDENTITY
Không migrate binary artifacts vào Supabase Storage trong đợt này. Việc đó làm đổi cả URL, access policy, lifecycle và chi phí egress. Chỉ cân nhắc sau khi database cutover ổn định.

09 · Change window

Production cutover runbook

  1. Thông báo maintenance. Chặn command/write mới và đóng UI actions có thể sinh operation/turn.
  2. Drain workload. Đợi task hoàn tất hoặc interrupt có kiểm soát; lưu trạng thái trước khi dừng.
  3. Dừng daemon. Xác nhận không còn process ghi SQLite và không còn child agent có thể commit muộn.
  4. Tạo backup nhất quán. Checkpoint WAL/SQLite backup API; hash và khóa read-only bản backup.
  5. Chuẩn bị Supabase. CI push migrations qua direct URL; xác nhận version, extensions, grants và runtime role.
  6. Final import. Import theo batch/transaction, giữ nguyên IDs, chạy setval và rebuild search index.
  7. Chạy verifier. Counts, PK, FK, JSON, time, numeric, artifacts, sequences và golden search.
  8. Switch config. Trỏ runtime sang direct/session pooler URL đã phê duyệt; không sửa SQLite backup.
  9. Read-only smoke. Test Team, Spy, Training, MCP, CLI; xác nhận anon/Data API không đọc được private data.
  10. Mở writes. Theo dõi lỗi, region latency, connections, locks, quota, disk và restart recovery.
10 · Recovery contract

Rollback không làm mất dữ liệu

Trước first Supabase write

Có thể dừng app, đổi config về immutable SQLite backup và chạy lại verifier. Đây là rollback sạch.

SAFE ROLLBACK

Sau first Supabase write

Không được flip trực tiếp về SQLite vì backup thiếu delta. Chỉ forward-fix Postgres hoặc reverse-export delta rồi verify.

NO BLIND FLIP
Điểm không thể thương lượng: rollback plan phải được rehearsal trước change window. SQLite chỉ bị xóa sau observation window và Supabase restore drill thành công.
11 · Definition of Done

Tiêu chí hoàn tất

Data & behavior

  • 100% bảng đạt count/PK/FK/JSON verification.
  • Không mất cursor, ID, millisecond, Unicode hoặc numeric precision.
  • Team, Spy, Training, MCP và CLI giữ nguyên contract.
  • Transcript search đạt golden acceptance corpus.
  • Không còn hidden read/write vào SQLite.

Operations & governance

  • Readiness phản ánh đúng connectivity và schema version.
  • Graceful shutdown đóng toàn bộ pool.
  • Backup/restore drill đạt RPO/RTO đã phê duyệt.
  • Không có database password/secret key trong frontend hoặc distributed binary.
  • Schema migration có thể tái lập bằng Supabase CLI từ Git.
  • SDD/ADR/README/runbook không còn mâu thuẫn source of truth.
  • SQLite backup retention và ngày decommission được ghi rõ.
Release decision: chỉ đánh dấu migration hoàn tất khi tất cả hard gates pass và không còn bước bắt buộc nào dựa trên “sẽ làm sau”.
